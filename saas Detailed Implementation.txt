Detailed Implementation Examples: Critical Multi-Tenancy Components
1. Data Migration & Rollback Strategy
Migration Architecture Pattern

Design a versioned migration system that treats tenant separation as a state machine. Each migration should be reversible with clear checkpoints.

Migration States:

    Pre-Migration Validation State: System runs with dual-writes (old logic + new scoping) but reads from old logic. Compare results to ensure consistency.

    Migration Execution State: System writes to new schema while maintaining old structure. Data transformation happens in batches with progress tracking.

    Post-Migration Verification State: System runs with new scoping but can fall back to old logic if anomalies detected.

    Cleanup State: Old structure removed after verification period (e.g., 30 days of production validation).

Rollback Triggers:
Define automatic rollback conditions:

    Data count mismatch exceeding 0.1% across any table

    Query performance degradation exceeding 200ms for critical operations

    Orphaned records appearing in audit logs

    Failed foreign key constraints during transaction commits

    Anomaly detection alerts from monitoring systems

Migration Monitoring:
Create a real-time dashboard showing:

    Progress per table (rows processed, success/failure rates)

    Data integrity metrics (orphaned records, constraint violations)

    Performance impact (query timing before/after)

    Rollback readiness status

2. Tenant Context Propagation
Context Lifecycle Management

Design a tenant context propagation system that maintains isolation across synchronous requests, asynchronous tasks, and background jobs.

Context Sources (in priority order):

    Explicit tenant parameter in function calls (highest priority)

    Request context from authentication middleware

    Session data for long-running operations

    Task metadata for background jobs

    User association as fallback with strict logging

    System default only for platform-level operations (blocked for school-level data)

Propagation Patterns:

For HTTP Requests:
Middleware extracts tenant from authentication token (school code), validates against active subscriptions, and establishes context before routing. All downstream operations inherit this context automatically.

For Background Tasks:
When enqueuing tasks, serialize tenant context into task metadata. Worker processes restore this context before executing, ensuring async operations maintain isolation. Failed tasks retain tenant context in logs for debugging.

For Database Operations:
Use a query interceptor pattern that automatically injects tenant filters without modifying business logic. The interceptor validates tenant context exists before executing any query on tenant-scoped tables. Platform-level tables bypass this filter.

For External Integrations:
Webhook handlers receive tenant context from URL parameters, headers, or payload data. Context is validated against signature before processing to prevent spoofing.

Error Handling:
When tenant context is missing for a tenant-scoped operation:

    Log the incident with stack trace and request details

    Block the operation (fail closed)

    Return appropriate error response (403 or 500 based on scenario)

    Alert monitoring systems for pattern detection

3. Hierarchical RBAC & Access Control
Multi-Level Access Structure

Design a hierarchical role system that supports platform-level and tenant-level access with clear separation boundaries.

Platform-Level Roles:

System Owner (Super User):

    Complete platform access across all tenants

    Can view all schools, subscriptions, and platform metrics

    Can modify system-wide settings and configurations

    Can access audit logs across all tenants

    Can perform emergency maintenance and migrations

    Cannot modify school data directly without explicit override (audited)

    Has ability to impersonate any user with full audit trail

Platform Support Staff:

    Can view all schools but with limited modification rights

    Can assist schools with troubleshooting

    Can reset passwords with approval workflows

    Can view support tickets across all schools

    Cannot access financial data or modify subscription plans

    All actions logged with school context and support ticket reference

    Requires secondary approval for sensitive operations

System Marketers (Portfolio-Based):

    Assigned to specific schools as their portfolio

    Can view assigned school's basic information and contact details

    Can view subscription status and usage analytics

    Can generate marketing reports for assigned schools

    Cannot access student data, financial records, or academic information

    Can communicate with school admins through the platform

    Portfolio assignments managed by System Owner

    Performance metrics tracked per marketer for their portfolio

Platform Auditors:

    Read-only access to all audit logs across schools

    Can view compliance reports and access patterns

    Cannot modify any data

    Separate authentication with MFA requirements

    All queries logged with auditor identity

School-Level Roles:
Each role inherits from the school context and cannot cross tenant boundaries:

    School Admin: Full school management, can create staff and manage settings

    Academic Admin: Manages classes, subjects, exams, and grading

    Finance Admin: Handles fees, payments, and financial reports

    Department Head: Manages department-specific resources and teachers

    Teacher: Access to assigned classes, grade entry, and student records

    Parent: Access to own children's records, fees, and communications

    Student: Limited access to own profile, assignments, and results

Permission Inheritance Rules:

    Platform roles cannot automatically access school data without explicit permission

    School roles cannot access other schools under any circumstances

    Cross-school reporting requires platform-level aggregators with data anonymization

    Role hierarchies support feature-based permissions (view, create, edit, delete, approve)

4. Subscription Enforcement Architecture
Subscription State Machine

Design a state-based subscription system with clear transitions and enforcement points.

Subscription States:

    Trial: New schools get 14-day trial with full features, upgrade prompts appear after 7 days

    Active: Full access based on plan features, payment up to date

    Grace Period: 7 days after payment failure, read-only access, warning banners displayed

    Suspended: After grace period, no access to school data except billing portal, admin can restore with payment

    Expired: Manual cancellation, data retained for 90 days, no access except data export request

    Archived: After retention period, data moved to cold storage, school code released for reuse

Enforcement Points:

At Authentication Level:

    Validate subscription status before establishing session

    Block login attempts for suspended/expired schools with clear messaging

    Display subscription status in dashboard banner

At Request Level:

    Middleware checks subscription status before processing any request

    Read operations allowed in grace period with warnings

    Write operations blocked in grace period except payment-related endpoints

    API rate limits reduced for non-active subscriptions

At Feature Level:

    Feature flags control access based on subscription plan

    UI components conditionally render based on available features

    API endpoints validate feature access before processing

At Data Level:

    Background jobs check subscription status before processing

    Data exports limited to active subscriptions

    Scheduled reports paused for inactive subscriptions

Notification Triggers:

    Trial ending (3 days before)

    Payment failed (immediate)

    Grace period started (1 day after payment failure)

    Suspension warning (3 days before suspension)

    Data archival warning (30 days before deletion)

Revenue Recovery:

    Automated dunning emails with payment links

    Retry failed payments with increasing intervals

    Offer payment plan options for larger invoices

    Track recovery rate per school segment

6. Audit Logging & Monitoring
Comprehensive Audit System

Design an immutable audit trail that captures all tenant-scoped actions with forensic detail.

Audit Log Structure:
Each log entry captures:

    Identity Layer: User ID, username, role, school ID (if applicable), session ID

    Request Layer: IP address, user agent, request ID, endpoint, method, duration

    Action Layer: Action type, resource type, resource ID, operation (CRUD)

    Data Layer: Before state (JSON), after state (JSON), reason for change, approval reference

    Context Layer: Correlation ID (links related actions), parent action ID, batch ID

    Compliance Layer: GDPR consent reference, legal basis, data retention category

Log Categories:

    Authentication Events: Login attempts, password changes, MFA verification, session creation/expiry

    Authorization Events: Permission checks, role assignments, access denials

    Data Events: Create, read, update, delete operations with data snapshots

    System Events: Configuration changes, background jobs, scheduled tasks

    Security Events: Suspicious patterns detected, rate limit hits, anomaly alerts

    Compliance Events: Data exports, consent changes, deletion requests

Storage Strategy:

    Hot storage (30 days): Fast query for troubleshooting

    Warm storage (90 days): Compressed, indexed for compliance queries

    Cold storage (7 years): Immutable archives for legal retention

    Separate write-once storage for compliance-critical logs

Monitoring & Alerting:

Real-time Anomalies:

    Sudden spike in cross-tenant query attempts

    Unusual data access patterns outside working hours

    Multiple failed authentication attempts across tenants

    API calls from unexpected geographic locations

    Data export volume exceeding typical patterns

Business Metrics:

8. Performance Optimization Strategy
Query Optimization & Caching

Database Optimization:

    Composite indexes for common query patterns (school_id + date ranges)

    Partition large tables by school_id for improved maintenance

    Materialized views for complex reports with refresh schedules

    Query plan analysis for tenant-scoped operations

    Connection pooling with tenant affinity for reduced context switching

Caching Strategy:

Request-Level Cache:

    Tenant configuration cached per request (subscription, features, settings)

    User permissions cached with invalidation on role changes

    Rate limit counters stored with school/user keys

Application-Level Cache:

    Frequently accessed data (school settings, term dates) cached with tenant key

    Report results cached with configurable TTL based on data volatility

    Dashboard aggregates precomputed during off-peak hours

Distributed Cache:

    Redis clusters partitioned by tenant for isolation

    Cache keys prefixed with school_id to prevent cross-tenant leakage

    Stale-while-revalidate pattern for high-traffic endpoints

Background Processing:

    Queue tenants with similar workloads together for efficiency

    Tenant-aware scheduling that respects subscription tiers

    Resource allocation based on school size and activity

Scaling Considerations:

    Read replicas with tenant-aware routing

    Sharding strategy for database growth (by school size or region)

    Connection pool sizing based on active tenant count

    Automated scaling triggers based on tenant workload patterns

1.3 Billing System Implementation

Subscription Management Tables:

Design tables that track school subscriptions, module assignments, and usage metrics. Each subscription has a parent record linking to the school, with child records for each selected module. Include start dates, end dates, trial periods, and billing cycles.

Usage Tracking Tables:

Create usage tracking per school per module with daily, monthly, and annual aggregates. Track metrics like student count (for per-student billing), API calls, SMS messages sent, and storage usage. This enables usage-based billing and capacity planning.

Pricing Tables:

Store pricing rules as flexible configurations rather than hardcoded values. Each module has base pricing, per-unit pricing, volume discounts, and promotional pricing periods. Support different currencies and tax rules based on school location.

Billing Engine Design:

The billing engine runs on a schedule to:

    Calculate monthly charges based on module selection and usage metrics

    Apply volume discounts (e.g., discount per module when selecting 5+ modules)

    Generate invoices with line items per module

    Track payment status and apply late fees

    Handle prorated charges for mid-cycle module additions

    Calculate refunds for module removals

Invoice Generation:

Each invoice includes:

    School details and billing period

    Line items: Module subscription fees, usage-based charges, discounts

    Payment due date and accepted methods

    Tax breakdown by jurisdiction

    Previous balance and adjustments

    Payment link for online payment

Payment Processing:

Integrate with payment gateways (Stripe, PayPal, local payment processors) with:

    Automatic monthly billing

    Payment method storage with tokenization

    Failed payment retry logic with increasing intervals

    Manual payment recording for offline payments

    Reconciliation tools for finance teams
